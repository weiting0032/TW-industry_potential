# 台股 AI 產業鏈 · 每日本益比追蹤選股 App

自動抓取台股每日收盤資料，將 AI 產業鏈標的分門別類，
**依本益比由低至高排序**，並自動框選出「估值低於同業、技術面未走壞」的低基期潛力股。

---

## 2. 環境建置與執行

需求：**Python 3.10 以上**（排程環境為 3.12、本機開發為 3.13）。
Windows 使用者請跑 `run.ps1`，`run.sh` 是給 macOS／Linux 的。

### 最快方式

```bash
./run.sh
```

腳本會自動建立 `.venv`、安裝相依套件並開啟 App。

### 手動安裝

```bash
python3 -m venv .venv && source .venv/bin/activate && pip install -r requirements.txt
```

接著啟動：

```bash
streamlit run app.py
```

瀏覽器開啟 <http://localhost:8501> 即可使用。

> **憑證錯誤排除**：若出現 `CERTIFICATE_VERIFY_FAILED`，代表 Python 缺少根憑證。
> 本專案一律透過 `requests`（自帶 certifi）連線已可避開；
> 若其他套件仍報錯，執行 macOS 內附的
> `/Applications/Python\ 3.x/Install\ Certificates.command` 即可。

### 三種檢視模式

1. **產業明細** — 單一產業成分股，預設依本益比由低至高；黃底為低基期候選。
2. **低基期總表** — 跨全部次產業彙整符合條件的個股，附低基期分數排行。
3. **產業總覽** — 各次產業估值比較（本益比色階）、低基期檔數分佈、全體成分股排序。

三種模式共用側邊欄的**代號／名稱搜尋**；搜尋只過濾表格內容，
產業基準仍以完整成分股計算，不會因為過濾而被扭曲。

畫面頂端固定顯示**資料健康度**：資料日期、成分股數、本益比覆蓋率。
最新快照超過 4 個平日沒更新會跳警告（排程斷了要看得出來）；
本益比覆蓋率低於 50% 也會提示（多半是交易所當日尚未公布）。

### 低基期篩選條件（側邊欄可調）

| 條件 | 說明 |
|---|---|
| 本益比低於產業基準 | 預設用**中位數**而非平均數 —— 台股單一產業常有一兩檔本益比破百，平均數會被拉高到幾乎人人「低於平均」 |
| 股價站上季線 (MA60) | 估值便宜但趨勢未壞；容忍度可放寬到跌破季線 N% 內，用來抓剛回測季線的標的 |
| 距 52 週高點回檔 ≥ N% | 排除已在高檔的個股 |
| 本益比絕對上限 | 選填，避免整個產業都貴時仍選出高本益比個股 |

**低基期分數** = 估值折價幅度 × 0.5 + 距高點回檔幅度 × 0.5，分數越高越「低基期」。

沒入選的個股會在「未達標項」欄位列出還差哪一條（估值／季線／回檔），
直接對應左側可調整的滑桿，不必自己回推。

**PE 歷史分位**（只顯示、不參與篩選）= 目前本益比落在該股**自身近一年**分佈的第幾百分位，
0 代表一年來最便宜。它補的是產業橫向比較的盲點：矽光子的產業本益比基準高達 90 以上，
「低於同業中位數」仍可能是一檔絕對值很貴的股票。
母體只取所選交易日**以前**的快照（回看歷史時不能用到當天之後的資料），
樣本不足 30 個交易日則顯示「—」而不給一個看似精確的數字。

## 4. 資料處理上的幾個關鍵決策

**本益比的「未獲利」判定**
交易所對虧損公司的表示法不一致：上市用 `-`、上櫃可能是 `0` 或空白。
三者一律歸為「未獲利／負值」，且**不列入低基期候選**（沒有 E，本益比低沒有意義），
並透過 `pe_sort = NaN → +∞` 讓它們在升冪排序時自然沉底。

**產業基準剔除離群值**
本益比 > 300 視為失真（多半是獲利趨近於零），不納入產業基準計算。

**均線的股價還原**
`yfinance` 在 `auto_adjust=False` 下，`Close` 已針對**除權配股**還原，但不對**現金股利**還原。
實測 2025-09-01：2330／3661／3324（僅配息）與交易所收盤價完全相同，
3163 波若威（有配股）則為交易所 240.00 vs yfinance 204.26。
這正是算均線需要的行為 —— 配股造成的價格斷層被抹平、季線不會被除權跳空扭曲，
同時最新一根 K 棒仍與交易所公告收盤價一致，兩者可直接比較。

**漲跌幅的缺口回補**
少數個股當日 `漲跌(+/-)` 欄位為 `X`（無漲跌參考價，多見於除權息或變更交易），
此時改用歷史資料的前一日收盤價回推漲跌幅。

**交易日解析用小 API，不用大 API**
不自建台股行事曆，改問證交所 FMTQIK（每日市場成交資訊）拿當月交易日清單 ——
只有約 0.6 KB，卻能一次判斷整月哪天有開盤；跨月時往前一個月再問一次。
這一步必須在查快取「之前」完成（要先知道日期才能組快取鍵），
所以刻意不能用 4.5 MB 的收盤行情 API 來探測，否則每次開 App 都會白抓一次全市場資料。
FMTQIK 若失效，會退回逐日探測收盤行情 API。

**本益比 API 比收盤行情晚公布 —— 排程時間的依據**
台股 13:30 收盤，但本益比不是收盤就有。實測台北時間 15:08：
證交所 `BWIBBU_d` 回「很抱歉，沒有符合條件的資料!」、櫃買 `peQryDate` 回 0 筆，
此時抓到的只有價量。原本排在 15:00 的班次剛好落在這個空窗，
會寫出「有價無本益比」的空殼快照 —— 而本益比正是這個 App 的核心欄位。
因此主要班次改到 17:00，並且：

- 上市改用 `MI_INDEX`「每日收盤行情(全部)」自帶的本益比欄位當備援（收盤後即有）
- 略過條件從「檔案存不存在」改成「**資料完不完整**」，讓後面的班次會修前面的爛攤子
- 完整度**上市與上櫃分開算**再取較低者：上櫃還沒公布時，光靠上市那半邊就能讓
  整體覆蓋率衝到七成、輕鬆越過門檻被誤判為完整，上櫃成分股就永久缺那一天
- 補跑時若新抓到的資料比既有快照差（例如某個交易所暫時斷線），保留舊檔不覆蓋

**產業字典擴編後，舊快照會自動回補**
完整度同時檢查「成分股有沒有到齊」。新加的股票在舊快照裡整列都不存在，
只看本益比覆蓋率的話舊快照會被判定為完整、永遠不補。
所以 `INDUSTRY_MAP` 加了新股之後，重跑 `--backfill N` 就會把歷史補上。

**歷史股價只下載一次**
回補歷史快照時同一批股票會被要求 250 個不同的 `as_of` 日期。
若每個日期各下載一次就是 250 次全批下載，又慢又容易被 Yahoo 限流中斷。
改成在同一個 process 內把收盤價寬表記憶起來（`history.close_history`），
之後每個日期只是切片再算一次均線 —— 實測 105 檔 × 3 年只要 3.3 秒。
`HISTORY_PERIOD` 取 3 年而非 1 年也是為了回補：回到一年前那天時，
往前仍需 250 個交易日才算得出 52 週高低點，1 年的區間會整片變成 NaN。

**對交易所友善**
同一主機的請求最少間隔 3 秒、失敗重試 3 次並指數退避；
當日資料以 parquet 落地快取，重開 App 不會重複打 API。

**企業內網的 TLS 攔截**
公司內網常有中間盒把 HTTPS 拆開重簽。實測本機連 `www.tpex.org.tw` 會間歇性拿到
`CERTIFICATE_VERIFY_FAILED: Missing Subject Key Identifier` ——
代理重簽的憑證缺 Subject Key Identifier 擴充欄位，OpenSSL 3.x 的嚴格檢查會拒絕，
而 `requests` 預設只信任 certifi 內建清單、看不到企業 CA。
安裝 `truststore` 後改用作業系統憑證庫驗證即可解決（企業 CA 本來就裝在那裡）。
這是換一個正確的信任來源，**不是**關閉驗證 —— 不要改成 `verify=False`。
沒安裝時程式自動略過，GitHub Actions 與 Streamlit Cloud 都不需要它。

## 5. 更新時機與部署

本專案採**資料與 UI 分離**：GitHub Actions 排程負責抓資料並 commit 快照，
Streamlit Cloud 上的 App 只讀 repo 內的 parquet，前端完全不對外連線。

```
GitHub Actions（每交易日 17:00／20:00／23:00 台北時間）
   scripts/check_universe.py → 產業字典對帳
   scripts/fetch_daily.py
   → 抓證交所／櫃買／yfinance
   → 寫 data/snapshots/YYYYMMDD.parquet（約 23 KB／日）
   → commit & push
                    ↓
Streamlit Cloud App
   → 只讀 data/snapshots/*.parquet，零網路請求，約 0.05 秒
```

三個班次不是重工：快照已完整會自動略過，只有不完整才重抓修補。

### 兩種執行模式

| 模式 | 觸發方式 | 行為 |
|---|---|---|
| 只讀快照（**預設**） | repo 內有快照就自動採用 | 只讀 `data/snapshots/`，零網路請求 |
| 即時擷取 | 側邊欄「資料來源」切過去 | 開 App 時抓交易所，有三層快取 |
| 強制只讀快照 | 設 `AISEMI_SNAPSHOT_ONLY=1` | 同上，且側邊欄不提供切換 |

**預設就是快照優先**：只要 repo 裡有快照，App 一律先讀快照。
這樣即使部署到 Streamlit Cloud 時忘了設 secret，雲端也不會從國外 IP 直打證交所
（那會讓冷啟動抓 4.5 MB 收盤行情再跑 105 檔 yfinance，慢到近乎當掉）。
`AISEMI_SNAPSHOT_ONLY` 現在的角色是「連切換選項都不要出現」，而不是啟用快照的開關。

設定管道兩種都支援：

```bash
# 本機／Docker／一般 VPS
AISEMI_SNAPSHOT_ONLY=1 streamlit run app.py
```

Streamlit Community Cloud **沒有環境變數介面**，也不會把 secrets 注入 `os.environ`，
因此改在 App 設定的 **Secrets** 欄位貼上：

```toml
AISEMI_SNAPSHOT_ONLY = "1"
```

### 部署到 Streamlit Community Cloud

1. 把整個專案推上 GitHub（`data/snapshots/` 要一起 commit）
2. Repo 的 **Settings → Actions → General → Workflow permissions** 選 **Read and write**，
   否則排程無法把快照 push 回來
3. 到 share.streamlit.io 連上 repo，主程式選 `app.py`
4. （選用）在 App 的 Secrets 貼上 `AISEMI_SNAPSHOT_ONLY = "1"`，
   讓側邊欄連「即時擷取」選項都不出現 —— 不設也不影響，預設本來就讀快照

歷史快照已隨 repo 一起 commit，不需要在雲端回補。
若日後要加長歷史或補上新加入的成分股：Actions 分頁 →「每日抓取台股收盤快照」→
Run workflow，`backfill` 填天數即可。

### 排程的已知限制

- GitHub Actions 的 cron 是 **UTC**，且尖峰時段可能延遲數十分鐘，所以排了 17:00／20:00／23:00 三班；
  後面的班次若發現快照已完整會自動略過，不完整才重抓修補
- **repo 連續 60 天沒有任何 commit，GitHub 會自動停用排程工作流程**。
  本專案每個交易日都會 commit 快照，正常情況不會觸發，但長假後值得確認一下
- Actions runner 是**美國資料中心 IP**。證交所與 Yahoo Finance 對這類 IP 的限流較嚴格，
  這是此方案最主要的風險。`http.py` 已內建 3 秒節流與 3 次指數退避重試；
  若仍持續失敗，就得改用台灣機房的 VPS 跑排程

### 手動操作

```bash
python scripts/check_universe.py             # 產業字典對帳（代號／市場別／名稱）

```

### 純本機執行時的更新時機

**不設 `AISEMI_SNAPSHOT_ONLY` 時是「開啟時才抓」，不是背景排程。** 沒人開 App 就不會有任何請求。

| 層級 | 內容 | 時效 |
|---|---|---|
| `st.cache_data` | 記憶體內的完整資料集 | 6 小時 |
| `market_*.parquet` | 上市＋上櫃全市場快照 | 12 小時 |
| `tech_*.parquet` | 均線與 52 週高低點 | 20 小時 |

開 App 時只會打一次 0.6 KB 的 FMTQIK 解析交易日；快取有效就直接讀檔（約 0.15 秒）。
快取過期或按下「🔄 重新抓取」才會真正重抓四支資料 API 加 yfinance。
